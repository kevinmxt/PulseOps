# PulseOps 路线图审查与调整建议

审查日期：2026-10-22

## 1. 结论

原 Phase 1–6 顺序总体合理，不需要推翻。建议做三项调整：

1. 在 Phase 2 前插入一个小而明确的 **Phase 1.1：可靠性修复门槛**，先修复配置更新与 in-flight probe 的竞态。
2. 将 Phase 4 拆成“核心 UI”和“认证/数据维护”两个子阶段；认证是公网部署的硬性门槛。
3. 在进入商业化讨论前增加“真实使用验证”，以误报/漏报、告警延迟、维护负担和用户留存为证据，不提前做计费、多租户或 AI 根因分析。

## 2. 推荐路线

### Phase 1.1：核心可靠性复核（新增，短阶段）

目标：修复影响结果正确性和公网部署安全边界的问题，不做大规模重构。

- [ ] 为探测结果增加配置版本/快照校验，避免旧配置结果覆盖新配置。
- [ ] 明确所有探测配置变更后的调度行为。
- [ ] 验证 DNS 超时在压力下的资源边界。
- [ ] 明确 SSRF 地址分类策略并补充 IPv4/IPv6 测试。
- [ ] 增加 CI：后端 verify、前端构建。
- [ ] 更新 Phase 1 验收文档，区分历史测试记录与当前 CI 证据。

完成门槛：配置变更竞态测试通过；执行期 SSRF 测试通过；CI 在干净 checkout 中通过。

### Phase 2：Incident 与通知（保留）

推荐实施顺序：

1. 先定义状态机和阈值语义。
2. 用数据库约束保证每个 Monitor 至多一个活动 Incident。
3. 将状态转换与通知任务持久化放在一致的事务边界内。
4. 用独立 worker 发送通知，设置有限重试、退避和可观测状态。
5. 再接入 Telegram。

重点要求：
- 一次持续故障只创建一个活动 Incident。
- 故障与恢复事件有幂等键或等价去重策略。
- Telegram 网络故障不能阻塞探测 worker。
- 数据库提交成功但发送结果不确定时，重试不会无限重复通知。
- 失败阈值与恢复阈值可配置但要有合理默认值。

MVP 不需要引入 Kafka/Redis；PostgreSQL 持久化通知任务 + Spring worker 足够。

### Phase 3：Heartbeat（保留）

- 复用 Incident 与通知机制，不复制一套独立状态机。
- 心跳 token 使用高熵随机值；数据库只存不可逆摘要或等价安全表示。
- 日志、错误响应中不能出现完整 token。
- 超时扫描必须幂等；重复扫描不能重复创建故障事件。
- 测试撤销 token、无效 token、超时、恢复和应用重启。

### Phase 4A：最小可用 UI（建议拆分）

只实现真实使用所需的核心流程：
- Monitor 列表、创建/编辑/禁用/删除。
- 当前状态、最近检查时间、延迟。
- 历史结果分页。
- 活动 Incident 与通知状态。
- 心跳配置与复制上报命令。

不要过早做图表大屏、复杂主题和自定义仪表盘。

### Phase 4B：认证、数据维护与运维基础（公网前必需）

- 单用户认证、授权和会话安全。
- 未认证 API 的集成测试。
- 历史数据保留与分批清理。
- 备份、恢复演练。
- 日志轮转与基本运行指标。
- 生产配置启动检查，防止未认证管理 API 被公开。

如果 UI 只通过本机访问，认证可以稍后；但任何公网可访问的管理入口必须先完成认证。

### Phase 5：VPS 部署与运行验证（保留）

- 单 VPS + Docker Compose + Caddy。
- 数据库仅内网/回环访问，生产凭证由环境注入。
- HTTPS、最小开放端口、SSH 密钥登录。
- 自动备份，并实际恢复到新数据库验证。
- 外部健康检查和资源监控。
- 升级/回滚演练。
- 连续运行至少 7 天，记录误报、漏报、告警延迟、CPU、内存、数据库大小和重启情况。

### Phase 6：小规模真实试用与继续/停止决策（保留）

先自用至少 1–2 周，再邀请 3–5 位开发者试用。观察：
- 是否有真实监控目标持续接入。
- 误报/漏报是否可接受。
- 告警延迟是否满足需求。
- 部署与维护是否足够简单。
- 用户是否在第二周仍持续使用。
- 哪个功能是用户愿意付费的，而非仅口头表示感兴趣。

在获得这些证据前，不建议做支付、套餐、组织/团队、多租户、复杂 RBAC、AI 根因分析。

## 3. 建议新增的产品指标

| 指标 | 目的 |
|---|---|
| 探测调度延迟（实际开始时间 - 应执行时间） | 判断队列是否积压 |
| 探测成功/失败分类 | 识别目标故障与平台自身错误 |
| Incident 到首次通知的延迟 | 验证告警价值 |
| 重复通知率 | 验证幂等与去重 |
| 误报/漏报案例数 | 验证状态机阈值 |
| CheckResult 每日增长量与数据库大小 | 决定保留期限 |
| CPU/内存/连接池/线程积压 | 验证 S$50/月以内单 VPS 的可运行性 |
| 试用用户第 2 周活跃情况 | 判断是否有真实持续需求 |

## 4. 不建议当前做的事

- 暂时不要微服务化。
- 暂时不要为单实例场景引入 Kafka、Redis、Kubernetes。
- 暂时不要把 AI 功能作为核心卖点；先把可验证的监控、故障和通知做可靠。
- 暂时不要实现收费与多租户。
- 不要以测试数量替代测试质量或生产可靠性证据。

## 5. 路线图维护规则

每个 Phase 都应包含：
1. 目标与明确的非目标。
2. 需要修改的模块和数据库迁移。
3. 单元/集成/安全测试。
4. 可复现的验收命令。
5. 完成证据和已知限制。
6. 对后续阶段的影响。

路线图状态只能在验收证据存在后更新，不因代码“看起来完成”而直接打勾。
