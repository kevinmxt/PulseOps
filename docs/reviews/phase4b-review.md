# PulseOps Phase 4B 代码审阅报告

审阅对象：用户提供的 `PulseOps-master (4).zip` 源码快照  
审阅范围：Phase 4B 认证与授权、会话/CSRF、登录限流、历史数据清理、备份恢复脚本、验收证据与路线图  
审阅方式：静态源码审查、测试/CI/验收文档核对、Shell 脚本语法检查；未能在本环境重跑完整测试

## 1. 结论

**Phase 4B 可按仓库提供的验收证据判定完成，下一阶段可进入 Phase 5（VPS 部署）。** 本次静态审查没有发现应立即阻断阶段推进的明显高危缺陷。认证覆盖管理 API、CSRF 与会话控制、历史数据保留/分批清理、备份与独立数据库恢复演练均有对应实现和测试/文档证据。

但在将服务暴露到公网之前，建议处理或明确接受本报告的登录限流并发边界，并在目标 Linux VPS 上复核脚本执行权限、TLS/代理信任边界、备份权限与恢复流程。Phase 4B 完成不等于公网发布已完成。

## 2. 本次确认的优点

- **默认拒绝的管理 API 边界：** `SecurityConfiguration` 明确公开 session 引导、登录/登出、健康检查和心跳上报端点，其余管理 API 需要 `ADMIN`；未知路径默认拒绝。
- **浏览器会话安全：** 使用服务端 Session、HttpOnly 会话 Cookie、SameSite=Lax、CSRF Token/请求头、空闲超时和绝对 12 小时超时；改密后使该用户会话失效。
- **首次启动失败关闭：** 空用户表缺少引导凭据、用户名/BCrypt 哈希不合法，或非回环监听未启用 Secure Cookie 时会拒绝启动。
- **数据清理有界：** CheckResult 与已解决 Incident 使用索引、批量删除和独立短事务；每个 tick 有共享批次预算，OPEN Incident 不按时间清理。
- **备份恢复有防误操作设计：** 备份使用 custom 格式和 `pg_restore --list` 自检、临时文件、保留数量；恢复默认拒绝覆盖，并禁止恢复到源库/维护库。
- **恢复证据较完整：** `docs/quality/phase4b-acceptance.md` 记录了备份、恢复到独立数据库、Flyway/核心表对比、应用启动与认证 API 冒烟验证，并明确列出未覆盖的失败清理分支。
- **Phase 4A 遗留项已纳入验收：** 验收记录列出迟到响应、分页/轮询竞争和响应体 abort 的测试覆盖。

## 3. 发现与建议

### P2：登录限流的“检查—认证—记失败”不是原子操作

**涉及位置**
- `backend/src/main/java/dev/pulseops/auth/LoginRateLimiter.java`：`checkAllowed()`、`recordFailure()`
- `backend/src/main/java/dev/pulseops/auth/api/AuthController.java`：登录流程
- `backend/src/test/java/dev/pulseops/auth/LoginRateLimiterTest.java`

**观察**

登录流程先调用 `checkAllowed(key)`，密码认证失败后才调用 `recordFailure(key)`。单个请求串行时，现有测试能够验证第 6 次失败被限流；但多个请求并发到达时，它们可能在任何一次失败被记账前同时通过 `checkAllowed()`，导致同一限流键在一个窗口内实际执行超过 5 次密码验证。`ConcurrentHashMap` 保证单次 map 操作线程安全，但不能让这两个独立调用形成原子配额。

**影响**

这不会绕过正确凭据校验，也不代表当前存在认证绕过；它会削弱登录限流对并发暴力尝试的约束。该功能是公网前的安全控制，建议在正式公网开放前加固。

**建议**
- 将限流配额的检查/占用合并为原子操作，例如在每个 key 上使用 `compute` 更新窗口并原子地决定是否允许本次尝试；再根据实际结果决定失败/成功如何结算。
- 明确“尝试次数”是请求次数还是失败次数，并让并发语义与测试一致。
- 增加并发测试：多个线程同时对同一 key 发起尝试，断言允许的认证尝试数有明确上限。
- 保留按用户名与来源地址限流的策略时，考虑增加独立的来源地址维度保护，避免攻击者通过大量不同用户名制造大量独立 key。若 Phase 5 配置反向代理，只信任明确配置的代理来源转发的客户端 IP，不要直接信任任意 `X-Forwarded-For`。

**验收标准**
1. 并发请求不能在限流窗口内无界地越过配额。
2. 429 与 `Retry-After` 语义稳定，正常成功登录清除对应失败状态。
3. 大量不同 key 不会让限流状态失控或轻易清除仍有效的关键窗口。

### P3：限流 key 达到容量上限时会任意驱逐一个窗口

**涉及位置**
- `LoginRateLimiter.java`：`MAX_TRACKED_KEYS` 与 `recordFailure()`

**观察**

当新 key 到来且 map 达到 10,000 个条目时，代码先清理过期项；如果仍满，则通过 `windows.keySet().stream().findFirst()` 删除一个任意 key，再写入新 key。该策略控制了内存上限，但驱逐对象没有考虑窗口是否仍有效、失败次数或目标账号的重要性。

**影响**

在大量不同用户名/来源地址组合填满 map 的压力场景下，仍有效的限流窗口可能被驱逐，降低限流效果。这是容量保护与安全保证之间的权衡，不是普通使用场景下的直接故障。

**建议**
- 与 P2 一并考虑：采用按来源地址的独立桶、全局尝试上限，或明确的容量溢出策略（例如拒绝新 key 而不是任意删除有效窗口）。
- 增加达到 `MAX_TRACKED_KEYS` 的边界测试，验证既有有效窗口不会在没有明确定义的情况下被轻易移除。
- 记录限流状态溢出指标/日志，但不要记录密码、Cookie 或 CSRF 值。

**验收标准**
限流状态达到容量上限时，行为可预测、可测试，且不会静默削弱已建立的有效窗口。

## 4. 数据清理审查

- CheckResult 以 `started_at < cutoff` 严格早于截止点的记录为清理对象；边界语义与 ADR-0009 一致。
- 已解决 Incident 以 `resolved_at < cutoff` 为清理条件，OPEN Incident 不会进入清理查询。
- Incident 删除前统计其 PENDING delivery，随后依赖外键级联；到期但未完成的通知会随事件一起删除。这与 ADR-0009 一致，但意味着过期 PENDING 通知不会无限期重试，运维上应接受该保留策略。
- 单 tick 的共享批次预算、独立短事务和批间暂停有助于限制长事务与数据库压力。
- 生产启用前建议在实际数据规模下观察清理耗时、删除计数、表膨胀与索引效果；当前验收证据证明了测试语义，不等于已完成生产负载验证。

## 5. 备份恢复审查

- `backup.sh` 和 `restore.sh` 的 Shell 语法检查通过。
- 备份临时文件在失败时清理，归档自检通过后才移动为正式文件；备份保留按文件名排序删除较旧文件。
- 恢复脚本校验目标数据库标识符，默认不覆盖已存在数据库，并显式拒绝源库和 PostgreSQL 维护库。
- 恢复失败时尝试删除半成品目标库；验收文档明确说明这条失败分支尚未通过人为制造中途失败来演练，建议在 VPS 运维演练中补一次。
- ZIP 中脚本的 Unix 权限元数据为 `755`；本次 Python 解包后的工作副本显示 `644`，属于当前审阅环境的解包表现，不能据此断言仓库脚本没有执行位。部署时仍应在 Linux 上确认 `test -x scripts/backup.sh scripts/restore.sh`。
- 备份包含密码哈希和心跳令牌摘要，应维持严格文件权限，并考虑 Phase 5 的异地副本、加密和失败告警。
