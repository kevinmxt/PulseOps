# Phase 4A 完成后的路线建议

## 结论

Phase 4A 已按仓库验收文档完成，下一阶段建议进入 **Phase 4B：认证、数据维护与运维基础**。当前无需扩展前端功能或引入复杂架构；先补齐公网发布前的安全和可维护性门槛。

## Phase 4B 建议顺序

1. **认证与授权先行**
   - 单用户认证和安全会话；明确登录、登出、会话过期与 CSRF 策略。
   - 管理 API 默认拒绝未认证请求，heartbeat 上报端点按其 token 认证模型单独处理。
   - 增加覆盖 Monitor、Incident、令牌轮换/撤销等管理接口的未认证与授权集成测试。
   - 确保启动配置不会让未认证管理 API 被公网监听。

2. **配置与密钥安全**
   - 审核 Cookie 属性、反向代理头、HTTPS 强制、错误响应与日志脱敏。
   - 确认 heartbeat token 不进入访问日志、异常日志或分析数据。
   - 对生产环境配置做启动校验，缺少必要安全配置时快速失败。

3. **历史数据保留与分批清理**
   - 定义 CheckResult、已解决 Incident 与 Notification Delivery 的保留期限。
   - 清理采用可限批次、可观测、可重入的方式，避免长事务与锁表。
   - 测试清理任务与查询/投递任务并行时的行为。

4. **备份与恢复**
   - 自动备份 PostgreSQL，明确保留数量、存储位置和失败告警。
   - 将备份实际恢复到新数据库，验证数据可用性，而不只验证备份文件存在。
   - 记录升级/回滚步骤和密钥恢复流程。

5. **小规模运行观测**
   - 日志轮转、健康检查、CPU/内存/数据库体积、探测调度延迟和通知延迟。
   - 保持当前单实例约束；没有真实需求前不引入 Redis、Kafka、Kubernetes 或多实例调度。

## 可顺手纳入的前端修正

- 为监控详情与 Incident 列表查询增加过期响应保护。
- 将响应体读取阶段的 AbortError 统一映射为 `TIMEOUT`。
- 解决列表轮询与分页操作竞争时目标页可能丢失的问题。

这些属于体验与诊断可靠性改进，不应替代 Phase 4B 的安全硬门槛。

## 公网发布门槛

在认证/授权、未认证 API 测试、数据保留策略、备份恢复演练、HTTPS 与生产启动检查完成前，管理界面和管理 API 只应在受控的本机/私有环境使用，不得直接暴露到公网。
