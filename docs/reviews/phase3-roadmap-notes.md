# Phase 3 完成后的路线建议

## 不需要修正的部分
- Phase 4A 继续做最小可用 UI 是合理的。
- Phase 4B 仍然应把认证与数据维护作为公网前硬门槛。
- 当前阶段不需要引入 Redis、Kafka、Kubernetes 或多实例调度。

## 建议强化的部分
1. 把“单实例调度”继续写成明确的运行约束，避免未来误部署。
2. 把“通知 at-least-once 语义”写成长期契约，不要后续误改成会丢消息的实现。
3. Phase 4A 的 UI 不要一开始做得过重，先把核心监控闭环跑通。
4. 如果后面要做公网可访问管理界面，认证最好提前到任何公开监听之前，不要等到最后一步才补。
5. Phase 4B 的历史清理与备份恢复建议尽早设计，因为 Phase 3 已经开始产生更真实的运行数据。

## 推荐继续执行的顺序
1. 最小可用 UI
2. 认证与授权
3. 数据保留和清理
4. VPS 部署与恢复演练
5. 小规模试用
