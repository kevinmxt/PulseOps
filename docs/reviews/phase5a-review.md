# PulseOps Phase 5A 代码与部署审阅

## 1. 结论

**阶段判断：Phase 5A 的本地部署准备与 VM 验收基本完成，可进入 Phase 5B 的真实 VPS / 公网准备；但不能把 5A 结论等同于已具备公网生产就绪状态。**

本次审阅对象是上传的 `PulseOps-master (5).zip` 快照，重点核对 `compose.prod.yaml`、Dockerfile、Caddy、部署/回滚/备份/恢复/加固脚本，以及 `docs/quality/phase5a-acceptance.md` 中的验收证据。

从验收记录看，Phase 5A 的本地 VM 闭环比较完整：三服务健康、HTTPS 内部 CA、匿名 API 认证边界、容器资源与权限限制、备份加密上传模拟、恢复到独立数据库、镜像回滚、SSH/UFW 加固、重启恢复及全量测试记录均有具体命令与结果。源码脚本的 `bash -n` 检查全部通过。本次环境没有实际 Docker VM，因此这些 VM 结果属于仓库中记录的验收证据，不是本次独立重跑结果。

## 2. 主要优点

- **网络边界清晰：** 宿主仅发布 80/443，PostgreSQL 与 backend 没有宿主端口；Caddy 只反代 API 与健康端点，未将 `/actuator/metrics` 暴露给公网。
- **容器加固较完整：** backend 非 root、只读根文件系统、`cap_drop: ALL`、tmpfs、资源限制；各服务有 `no-new-privileges` 和有界 Docker 日志轮转。
- **部署门禁合理：** 部署前先备份，再构建、启动、等待健康状态并执行 smoke test；失败时不会声称自动回滚，而是输出恢复/回滚路径。
- **数据库迁移回退有保护：** rollback 检查记录的 Flyway schema rank，避免在较新数据库结构上直接启动旧镜像。
- **备份链路具备基本保护：** `umask 077`、dump 自检、age 加密、远端对象大小核验、保留策略及 systemd `OnFailure` 通知。
- **加固脚本有安全提示：** SSH 配置验证失败会回退 drop-in；输出要求保持当前 SSH 会话并用第二会话验证。

## 3. 问题与建议

### P1（Phase 5B 公网开放前必须完成）：真实异地备份与外部告警尚未接通

`phase5a-acceptance.md` 明确记录：rclone remote 当前是 VM 内本地目录，`HEALTHCHECKS_PING_URL` 未配置，成功/失败 ping 只通过本地 HTTP 接收器模拟。该方案足以验证脚本控制流，但不能提供宿主机/磁盘故障之外的灾难恢复能力，也不能证明真实外部告警链路有效。

**建议：** Phase 5B 将 remote 替换为真实独立对象存储/账户，启用真实 Healthchecks 或等效外部监控；确认 age 私钥有离线安全副本；故意制造一次备份失败并验证外部告警；从真实远端对象下载、解密、恢复并启动应用，记录 RPO/RTO。不要将“脚本成功”误当成“异地灾备已验证”。

### P1（公网开放前必须完成）：真实域名、ACME 与浏览器端到端流程未在 5A 验收

当前站点为 `pulseops.test`，使用 Caddy 内部 CA。验收文档明确将真实域名、ACME 证书、公网可达性与自动化浏览器登录/创建监控流程划入 5B。内部 CA TLS 链通过只能证明本地预演配置有效。

**建议：** 在真实 VPS 配置 DNS、80/443 入站与 ACME 邮箱后，从外部网络验证完整证书链、HTTP→HTTPS 跳转、登录、创建/编辑监控、心跳配置、Incident 与通知流程；同时确认不再使用 `--insecure` 或本地 hosts 解析作为验收替代。

### P2：生产镜像基础镜像使用可变标签

`compose.prod.yaml` 使用 `postgres:17-alpine`；前端 Dockerfile 使用 `caddy:2-alpine`。这类标签会随上游更新而变化，降低重建的可重复性，也可能在同一 Git commit 的不同时间构建出不同基础镜像。

**建议：** 在 Phase 5B 或后续加固中固定到经过验证的 patch 版本，条件允许时使用 digest pinning；建立定期更新、漏洞扫描与主动升级流程。不要仅因固定标签而长期不更新。

### P2：UFW 的 SSH `limit` 可能影响高频自动化运维

验收记录已观察到连续快速 SSH 命令触发 `ufw limit 22/tcp`，导致 SSH 短暂不可达，等待限速窗口后恢复。它不是应用故障，但可能中断部署脚本、批量运维或自动化探测。

**建议：** 生产自动化优先复用单个 SSH 会话/连接复用，避免短时间新建大量连接；部署前确认有控制台或云厂商救援入口。若调整限速策略，先评估 SSH 暴力破解风险，不建议直接移除保护。

### P3：访问日志与外部运维可观测性仍偏薄

验收记录说明 Caddy 未配置访问日志，应用与 Caddy 主要依赖 Docker `json-file` 日志；当前没有真实外部 uptime 监控，也没有 7 天连续运行证据。这对本地阶段可以接受，但正式运营时，异常请求趋势、真实客户端访问和证书/外部可达性问题的排查能力有限。

**建议：** 5B 至少接入外部 uptime/备份监控并配置通知；根据隐私与磁盘预算决定是否启用访问日志或结构化请求日志，确保日志不记录 Cookie、认证凭据、心跳令牌或其他秘密。完成连续运行观察并记录告警演练。

## 5. 阶段决策

Phase 5A 的目标是本地部署预演和部署工具准备，按现有证据可以收口。下一步建议进入 Phase 5B，但把“真实域名与 ACME”“真实异地备份”“真实外部告警”“公网浏览器端到端验收”“恢复演练与连续运行观察”设为公网开放门槛。镜像标签固定与日志完善属于建议的加固项。
