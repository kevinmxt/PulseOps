# ADR-0008: 管理认证采用数据库账号、服务端会话与 CSRF

- 状态：Accepted
- 日期：2026-10-25

## 背景

Phase 1–3 的管理 API 不做认证，默认只监听回环地址（ADR-0003）。Phase 4B 是公网发布前的硬门槛，要求应用自身拒绝未认证请求。管理界面是浏览器 SPA，需要登录、登出、会话过期与服务端失效；未来还计划支持多用户。

## 决策

- 使用 Spring Security 服务端 Session（内存存储）承载登录态，提供 JSON 登录、登出、会话引导与改密端点。
- 账号存入 `app_user` 表，用户名唯一，密码使用 BCrypt（`{bcrypt}` 前缀，成本因子 12）；角色字段暂只允许 `ADMIN`。
- 首次启动在用户表为空时使用环境变量引导管理员账号；认证始终启用，不提供关闭开关。
- 浏览器通过 `HttpOnly`、`SameSite=Lax` 的 `PULSEOPS_SESSION` Cookie 携带会话；空闲 30 分钟、绝对 12 小时。
- 使用双提交 Cookie 实现 CSRF：`XSRF-TOKEN` + `X-XSRF-TOKEN`，覆盖登录、登出、改密与所有管理写请求；心跳上报不使用 Cookie 认证，豁免 CSRF。
- 登录失败按用户名与远端地址限流；启动时校验凭据、哈希格式与非回环监听下的 Secure Cookie。
- 改密成功后使该用户的全部会话失效。

## 备选方案

- **HTTP Basic**：每个请求携带凭据，浏览器与前端容易缓存或存储密码，且没有服务端登出与过期控制。
- **前端 Bearer Token 存 `localStorage`**：XSS 时长期凭据直接泄漏；令牌撤销需要额外状态。
- **仅环境变量内存用户**：无法为改密、多用户和持久事实来源提供基础。
- **可关闭认证的开关**：会引入只在开发/测试存在的旁路，容易与生产行为漂移。
- **Spring Session JDBC**：单实例下增加表、清理和事务负担；重启保持登录不是本阶段目标。
- **`SameSite=Strict` 且关闭 CSRF**：在反向代理、子域与浏览器差异下过于脆弱。

## 后果

- 应用重启会使所有会话失效；这是单实例内存会话的预期代价。
- 所有非 GET 管理请求必须携带 CSRF 头；前端需要引导端点与一次失败重试。
- 非回环监听必须启用 Secure Cookie，Phase 5 必须由 Caddy 终止 TLS。
- 引导变量只在首次建号时生效；忘记密码需要按文档更新哈希。
- 反向代理后的真实客户端 IP 在 Phase 5 前不可用，登录限流可能共享同一计数。
- 多用户尚未实现；`role` 字段与唯一用户名为后续扩展保留空间，但当前所有账号都是 `ADMIN` 且没有资源归属。
- 现有集成测试需要认证上下文；测试不得通过关闭安全链来绕过。
