# ADR-0005: 事务性 outbox 与轮询通知投递

- 状态：Accepted
- 日期：2026-10-23

## 背景

Phase 2 需要在 Incident 打开与恢复时通过 Telegram 通知用户。通知不能阻塞探测线程，发送失败不能回滚已确认的故障状态，服务重启后不能重发已经发送的历史通知；当前是单实例部署，不引入额外消息中间件。

## 决策

在 Incident 创建或关闭的同一数据库事务中写入 NotificationDelivery（`PENDING`），由独立的 `fixedDelay` 调度任务（默认 5 秒、每批 50 条、批内串行、独立调度线程）按 `next_attempt_at` 领取并发送。投递状态持久化为 `PENDING` / `SENT` / `FAILED`；同一 Incident、事件类型与渠道唯一。选择 at-least-once 语义：发送成功但尚未标记 `SENT` 时崩溃，可能导致一次重复投递。

## 备选方案

- 同步发送：阻塞探测或事件处理线程，发送失败与状态事务耦合。
- `@TransactionalEventListener(AFTER_COMMIT)` + 内存异步执行：进程崩溃会丢失尚未发送的通知，无法重启后续发。
- 引入消息队列：单实例、个人使用场景下增加部署与运维复杂度，违背少依赖原则。
- 数据库 `LISTEN/NOTIFY`：需要额外监听连接与重连处理，对本规模收益有限。

## 后果

- 通知最多有一个调度间隔的延迟。
- 需要 NotificationDelivery 的到期索引；数据随使用增长，历史清理在 Phase 4B 处理。
- 接受极小概率的重复通知，不能依赖 Telegram 提供幂等键。
- 失败按可重试性处理：网络错误、5xx、429 最多尝试 3 次，退避 1 分钟与 5 分钟；其他 4xx 立即进入终态 `FAILED`。
- 仍假设单实例调度；支持多实例前需要数据库租约或原子认领机制。
