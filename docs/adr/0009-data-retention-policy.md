# ADR-0009: 历史数据保留期限与分批清理

- 状态：Accepted
- 日期：2026-10-25

## 背景

Phase 1–4A 持续写入 CheckResult、Incident 与 NotificationDelivery，没有删除策略。公网长期运行后表会无限增长，查询与备份成本上升。清理必须避免长事务、锁表，并且不能删除仍代表当前故障状态的 OPEN Incident。

## 决策

- `CheckResult` 保留 30 天，按 `started_at` 删除早于期限的记录。
- `RESOLVED` Incident 从恢复时间起保留 90 天，按 `resolved_at` 删除；其 NotificationDelivery 由外键级联删除。
- `OPEN` Incident 及其投递永不按时间清理；Monitor 删除仍由既有级联处理。
- 使用独立 `cleanup-tick-` 单线程调度器，默认每小时执行；单批 1000 行、每批独立短事务、批间暂停 50ms、单 tick 最多 50 批。
- 保留天数、批次大小、批次上限、tick 间隔均可配置并校验范围。
- 新增 `check_result(started_at)` 索引与 `incident(resolved_at) WHERE status = 'RESOLVED'` 部分索引。
- 到期仍滞留的 `PENDING` 投递随 Incident 一起删除并记录数量；通知投递器遇到已不存在的投递行按无操作处理。

## 备选方案

- **永久保留**：查询、备份和恢复成本持续增长，个人 VPS 存储有限。
- **按 Incident 开始时间清理**：会让“最近恢复但很久以前开始”的事件立即消失，不符合保留期直觉。
- **单独按期限清理 NotificationDelivery**：与 Incident 级联语义冲突，且会留下缺失投递的事件。
- **每个 Monitor 保留最近 N 条结果**：规则复杂，不能解决已删除或禁用监控项的历史占用。
- **数据库分区或定期重建表**：当前数据规模不需要，运维复杂度明显更高。

## 后果

- 超过保留期限的数据会永久丢失；这是有意设计，调试历史仅保证 30 天。
- 已解决事件的投递审计最多保留 90 天；需要长期归档时应在 Phase 5 结合备份策略处理。
- 到期未完成的投递会被删除；发送器必须容忍投递记录在读取后消失。
- 两个新增索引增加少量写入成本，但使全局期限删除可走索引扫描。
- 单实例调度约束不变；多实例前仍需要数据库租约或原子认领。
