# 安全规范

安全要求是 MVP 的必需条件。

## SSRF 与目标 URL
用户可配置目标 URL，因此所有探测目标均视为不可信输入。

必须：
- 只允许 HTTP/HTTPS。
- 只允许全球可路由的公共 IP 地址；拒绝其他所有地址。
- 对解析后的 IP 执行校验。
- 考虑 DNS 重绑定风险。
- 对重定向执行严格限制；禁止未经校验跳转到受限地址。
- 设置连接、响应和响应体大小限制。
- 创建时和每次执行时都进行必要校验。

不能可靠防护时，缩小允许访问范围；不能只在创建时检查 URL 一次。

### 地址分类策略

策略依据 IANA IPv4/IPv6 Special-Purpose Address Registries（查询日期 2026-10-22）维护显式受限前缀清单，而不是依赖零散的 `InetAddress` 分类方法：

- IPv4 受限前缀：`0.0.0.0/8`、`10.0.0.0/8`、`100.64.0.0/10`、`127.0.0.0/8`、`169.254.0.0/16`、`172.16.0.0/12`、`192.0.0.0/24`、`192.0.2.0/24`、`192.88.99.0/24`、`192.168.0.0/16`、`198.18.0.0/15`、`198.51.100.0/24`、`203.0.113.0/24`、`224.0.0.0/4`、`240.0.0.0/4`。
- IPv6 默认拒绝 `2000::/3` 之外的地址；在 `2000::/3` 内额外拒绝 `2001::/32`（Teredo）、`2002::/16`（6to4）、`2001:1::1/128`、`2001:1::2/128`、`2001:2::/48`、`2001:10::/28`、`2001:20::/28`、`2001:30::/28`、`2001:db8::/32`、`3fff::/20`。Teredo/6to4 可封装 IPv4，因此采取保守的整段拒绝；部分协议 anycast 地址也一并拒绝。
- IPv4-mapped IPv6（`::ffff:0:0/96`）和 NAT64（`64:ff9b::/96`）提取内嵌 IPv4 后复用 IPv4 判定；内嵌受限地址时整个解析结果被拒绝。已废弃的 IPv4-compatible IPv6（`::/96`）直接拒绝。`64:ff9b:1::/48` 等其他非全球单播前缀由默认拒绝规则处理。
- 一次 DNS 返回多个地址时，任一地址受限即拒绝该组结果。
- 继续禁止自动重定向，3xx 作为普通响应按预期状态码判定。

应用层校验不能替代网络隔离。部署时必须同时配置出站防火墙或等价策略，限制应用可访问的目标范围。

## 认证与授权
- 公网管理入口的发布门槛见 [`../quality/deployment.md`](../quality/deployment.md) 的“公网发布硬性门槛”；本节规定认证实现要求。
- 密码使用成熟的安全哈希算法。
- 正确配置 Cookie / Session 安全属性。
- 根据认证方式实施 CSRF 防护。
- 对登录失败进行限制。
- 对受保护接口进行未授权访问测试。
- 所有管理操作都要检查权限。

## 密钥与敏感信息
- 不将真实密钥、密码、Bot Token 或私钥提交到 Git。
- 使用环境变量或安全部署配置注入密钥。
- `.env.example` 只允许占位值。
- 不记录完整心跳令牌、密码和敏感请求头。
- 心跳上报按令牌摘要限流 120 次/分钟（无效令牌同样计数），请求体上限 1KB；生产环境通过 `pulseops.heartbeat.require-https` 强制 HTTPS（原生 TLS 或可信代理的 `X-Forwarded-Proto: https`）。
- 默认不记录被监控 API 的完整响应正文。
- 错误摘要必须截断并避免敏感信息。
- 不向用户返回内部堆栈、连接串或环境变量。

## 网络和部署
- PostgreSQL 不直接暴露到公网。
- 生产环境使用 HTTPS。
- 关闭无必要的公网端口。
- SSH 优先使用密钥认证。
- 使用权限受限的数据库账号。
- 保护备份文件和日志。
- 管理 API、心跳凭证和公开状态页必须具有清晰的权限边界。

## 安全测试最低范围
- 非法 URL 和协议
- localhost / 私有 IP / 链路本地地址
- 重定向到禁止地址
- 无效或撤销的心跳令牌
- 未认证访问管理接口
- 敏感信息日志检查
- 超长输入和非法配置
